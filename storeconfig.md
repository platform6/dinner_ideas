Shared Context (give this to both agents)

Problem statement: The current "Grocery store setup" page lets a user define an ordered list of store sections/aisles and separately map broad ingredient categories (Dairy, Grains, Pantry, Produce, Protein) to those locations. This doesn't match the real goal: connecting individual recipe ingredients to the specific place in the store where the user personally finds them, and reusing that knowledge intelligently (e.g., if "pinto beans" is already mapped to Aisle 2, "black beans" should be easy to map to the same place without re-doing the work from scratch). Not every ingredient needs a location — unassigned is a valid, expected state.

Core entities:

Location — a stop in the user's walking path through the store. Each Location has a name, a type (section e.g. "Dairy"/"Bakery", or aisle e.g. "Aisle 1"/"Aisle 2"), and a position in one single ordered sequence (sections and aisles interleave freely in this one path — there is no separate list for each type).
Item — an individual ingredient (e.g., "black beans," "pinto beans," "eggs"). An Item optionally links to one Location. Items are not required to have a Location.
Suggestion link — when a user is assigning a Location to a new Item, the system should surface Items that seem similar (by name/text similarity, and/or shared category if categories still exist as loose grouping metadata) and show where those were previously placed, so the user can accept "same place as pinto beans" in one action instead of hunting manually.

Known open questions — do not silently assume, ask the requester (Chandler) directly:

Should this store-config page allow inline creation/renaming of Items and their category grouping, or does that stay confined to the existing Catalog page, with this page only handling location assignment?
Is drag-and-drop reordering of Locations required, or are up/down arrow buttons (current behavior) acceptable?
Design Prompt (for the design agent)

Redesign the grocery store configuration page so its structure and language make the underlying model self-evident without needing help text to explain it. Currently the page shows two side-by-side panels — an ordered "Rows" list and a separate "Category Assignments" list — and because both panels list nearly identical names (Dairy, Grains, Pantry, Produce, Protein), it visually reads as duplicated data rather than two distinct concepts. Redesign this so it's immediately clear that there is one walking path (made of sections and aisles together, in order) and a separate, item-level action of placing an ingredient into a spot on that path.

Specific things to solve for: distinguish "section" stops (named, e.g. Dairy, Bakery) from "aisle" stops (numbered, e.g. Aisle 1, Aisle 2) visually within a single unified ordered list, rather than making aisles look like a different, lesser category of the same list. Design the item-to-location assignment flow so that when a user is placing an ingredient like "black beans," the interface proactively surfaces a suggestion such as "pinto beans is in Aisle 2 — put black beans there too?" as a lightweight, low-friction confirmation rather than a form field they must fill from scratch. Show, per Location, the multiple items/categories that live there (e.g., Bakery containing cupcakes, bread, and cookies) in a way that scales if a location has many items without becoming an unreadable wall of text. Preserve a clear, non-scary treatment for unassigned items — this is an expected, normal state, not an error — while still making it easy for the user to find and assign unassigned items if they choose to. Keep the two open questions above in mind as you design: leave room in the layout for possible inline editing of items/categories, and consider whether the reordering interaction should be arrows or drag handles, but don't treat either as settled.

Functionality Prompt (for the coding agent)

Build a data model and set of interactions that support the following. A Location entity has a name, a type field of either section or aisle, and a single shared position/order field so all Locations — regardless of type — sit in one ordered walking-path sequence. An Item entity represents an individual ingredient and has an optional foreign key to a Location; leaving it null is valid and expected, and should not trigger validation errors. Items are linked to recipes elsewhere in the app already (via ingredients); this Location field is additive metadata on the Item, not a replacement for existing recipe-ingredient relationships.

Implement a similarity-suggestion feature: when a user is about to assign a Location to an Item that doesn't have one yet, query previously-categorized Items for likely matches (start with simple approaches — substring/fuzzy string match on the item name, e.g. "beans" appearing in both "pinto beans" and "black beans" — and treat existing category/grouping metadata as an optional secondary signal if it still exists in the schema). Surface the top match(es) with their assigned Location, and let the user accept the suggestion in a single action (assigning the new Item to the same Location) or dismiss it and choose manually. This should be a suggestion only — never auto-assign without user confirmation.

Support many Items pointing to the same Location (e.g., cupcakes, bread, and cookies all pointing to a "Bakery" section) — this is the expected common case, not an edge case. Keep the existing "unassigned items appear after the ordered list, alphabetically" behavior for any Item without a Location. Do not build inline creation/editing of Items or category-grouping on this page yet, and do not build drag-and-drop reordering yet — both are explicitly open decisions; implement the simplest reasonable placeholder (e.g., keep current up/down arrow reordering) and leave clear extension points so either can be added later without a schema change.
